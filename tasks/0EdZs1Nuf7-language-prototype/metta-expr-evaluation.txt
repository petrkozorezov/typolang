Главное сходство — выражения служат одновременно данными, образцами и материалом для вычислительного переписывания.
В MeTTa можно определить правило так:
 
(= (take-left (cell $a $b)) $a)

!(take-left (cell Left Right))

Запрос получает Left: выражение сопоставляется с левой частью правила, найденные связывания используются в правой. Образец непосредственно имеет структуру кода — без
Y-expr: запись деревьев и экспорт в JSONпромежуточного макроса образцов. Это следует из описанного в спецификации устройства определений через =. Спецификация MeTTa (https://trueagi-io.github.io/hyperon-
experimental/metta/#function-expression)

Причём у них полезно разделены общий механизм и управление им. В минимальном ядре:

• unify сопоставляет выражения и получает связывания;
• eval выполняет шаг вычисления;
• chain организует вычисление и последующую подстановку.

Это близко к нашей идее общей основы для сопоставления и переписывания. При этом операции сохраняют разные контракты. Минимальное ядро (https://trueagi-io.github.io/
hyperon-experimental/minimal-metta/)

Есть четыре существенных отличия.

Первое — двусторонняя унификация. Переменные могут связываться с обеих сторон. В исходниках отдельно представлены отношения между переменными и их значения; сама
переменная не хранит присвоенное значение внутри себя. Это полезный пример разделения идентичности и связывания. Представление атомов (https://github.com/trueagi-io/
hyperon-experimental/blob/3f76dc460da6961f57f69f6c3e550c59c74ada83/hyperon-atom/src/lib.rs)

Но для наших holes это требует осторожного выбора семантики. Сейчас неизвестное исследуемое значение при проверке конкретного атома оставляет match открытым. Унификация
MeTTa может вместо этого связать неизвестную переменную с требуемым атомом — спецификация прямо обсуждает такое поведение unify. Сопоставление переменных (https://
trueagi-io.github.io/hyperon-experimental/minimal-metta/#syntax-to-match-atom-by-equality)

Второе — несколько результатов. MeTTa допускает альтернативные связывания и вычисления. Например, библиотечный match ищет все соответствующие атомы в пространстве. Наш
выбранный приоритет ветвей — другая семантика. Контракт match (https://trueagi-io.github.io/hyperon-experimental/generated/corelib/#match)

Третье — стратегия вычисления. Согласно документации, обычная MeTTa по умолчанию вычисляет аргументы перед передачей; метатипы позволяют менять это поведение.
Минимальное ядро передаёт аргументы без предварительного вычисления. Поэтому наше вычисление по востребованию с разделением работы нельзя считать уже полученным вместе с
их моделью переписывания. Порядок вычисления (https://trueagi-io.github.io/hyperon-experimental/minimal-metta/#evaluation-order)

Четвёртое — наши лексические связи. Базовый matcher MeTTa рекурсивно сопоставляет выражения и переменные; отдельного правила для соответствия объявлений вложенных lambda
в нём нет. Сохранение конкретных захватов и сопоставление связанных параметров нам всё равно нужно определить самостоятельно. Реализация matcher (https://github.com/
trueagi-io/hyperon-experimental/blob/3f76dc460da6961f57f69f6c3e550c59c74ada83/hyperon-atom/src/matcher.rs#L1098)

Мой вывод для нашего дизайна: стоит исследовать основу «выражение + связывания + правила переписывания». MeTTa даёт для этого конкретную реализацию, а не только
аналогию.

И она подсказывает следующий точный вопрос: какие неизвестные matcher имеет право связывать? Я бы начал с такого различия:

• открытые входы шаблона разрешено заполнять найденными фрагментами;
• неизвестные входы исследуемого выражения сохраняются неизвестными;
• соответствие внутренних объявлений устанавливается отдельно от заполнения входов.

Это моё предложение для typolang. Оно позволяет использовать holes в шаблонах, сохраняя нашу семантику незавершённой программы. А двустороннюю унификацию можно оценить
отдельно, не вводя её незаметно через обычный match.
