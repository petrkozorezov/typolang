# Расширяемая интерпретация форм

Интерпретацию форм выполняет библиотечная функция `parse`. Она использует
расширяемое сопоставление образцов с обработчиками, позволяющее вводить
пользовательские конструкции, включая связывающие, без отдельной макросной системы.
Это концептуальное направление; точный API ещё предстоит проработать.

## Формы и открытые выражения

[Чтение T-expr](syntax.md) строит дерево данных; `parse` получает форму и контекст,
в котором она приобретает смысл. Открытое выражение содержит функции, входы,
связи и захваты; исходная форма ещё не содержит установленных связей.

`parse` и обработчики — обычные ленивые функции языка. Если смысла формы уже
достаточно для преобразования, вызов `parse` редуцируется в соответствующее
выражение. Построение кода и запрос его редукции различаются явно;
интерпретация не обязана выдавать полностью нормализованную программу. Неизвестные зависимости
оставляют соответствующий фрагмент вычисления открытым.

Переход от форм как данных к коду происходит в ходе этого же вычисления.
Результат остаётся доступным программе выражением со связями. Принцип «код как
данные» сохраняется; отдельное непрозрачное представление кода не требуется.

## Распознавание и применение

Сопоставление правила может востребовать наблюдение первого элемента формы.
Для обычного вызова:

```text
foo.bar a b
```

`parse` наблюдает `foo.bar`. Когда получена lambda, форма сводится к применению
этой функции через `core.bind`. Лексические захваты функции сохраняются;
аргументы и их интерпретация остаются ленивыми. Связывание использует
обычные [правила применения](application.md), не вводя другой модели арности.
Для получения lambda достаточно внешней формы; обязательная головная редукция
её тела не нужна. Точная композиция получения функции, `bind` и запроса `reduct`
в обычной записи вызова ещё требует определения.

Распознавание формы и наблюдение её первого элемента могут чередоваться.
Предварительная интерпретация всех операндов не требуется: для связывающей
формы объявления должны появиться до разрешения зависимых обращений.
Нехватка информации для распознавания обрабатывается как открытая зависимость
самого вызова `parse`, без отдельного механизма ожидания.

Например, локальное правило может интерпретировать форму:

```text
a + b
```

Обработчик сводит её к применению функции сложения к `a` и `b`, сохраняя их связи.
Чтение при этом не меняется: оно даёт список из трёх символов.
Так можно расширять грамматику форм поверх T-expr, сохраняя правила чтения.

## Контекст и связывающие конструкции

Расширения подключаются явно в контексте модуля или более узкой области,
например карты. Отложенная интерпретация сохраняет этот контекст;
перенос фрагмента не должен менять набор правил, определяющих его смысл.
Способ объявления и передачи набора правил пока не выбран.

Контекст-карта содержит ссылки на базовые формы и обычные операции.
Затенение базовых форм запрещается валидатором, в том числе для построенного
кода. Имя базовой формы разрешается в ссылку; одно написание имени не определяет
её идентичность. Точный набор базовых форм, псевдонимы и доступность определений
при интерпретации ещё требуют проработки.

Связывающая форма должна создавать объявления до разрешения зависящих
от них обращений. Например, предполагаемая пользовательская форма:

```text
my-let ((x source))
  cons x nil
```

Её обработчик создаёт объявление `x`, связывает его с ленивым `source`
в исходном окружении и строит тело в расширенной области. Не требуется сначала
полностью разрешить все операнды, а затем пытаться изменить готовые ссылки.
Установленные ссылки сохраняют цели; защита от случайного захвата обязательна.

## Цитирование

После введения явных `bind/reduct` роль цитирования пересматривается в
[работе с кодом](code.md#цитирование-открытых-выражений). Реализация `quote/unquote`
через режим `parse` остаётся гипотезой. Обязательная цитирующая оболочка результата
`parse` не вводится; построение выражения само по себе не требует его исполнения.

## Мотивация и границы

В [прежней модели](../obsolete/macros-and-bound-code.md) отдельные макросы вводились
ради пользовательских связывающих форм: обычная функция не могла объявлять
имена в уже связанном теле.
Расширяемый интерпретатор переносит установление этих связей в обработчик формы.
Распознавание, разрешение имён и построение выражений становятся обычными
ленивыми вычислениями. Не нужны полное предварительное распознавание программы
или отдельный исполнитель для перехода от формы к выражению.

Цена — необходимость согласовать пользовательские правила с разрешением имён,
ленивостью и валидацией. Остаются открытыми API образцов и обработчиков,
приоритеты и конфликты правил, границы расширения базовых форм, объявление
локальных контекстов и гигиена.
Правила интерпретации форм и ветви вычислительного `match` решают разные задачи;
приоритет ветвей `match` не задаёт автоматически порядок выбора обработчиков форм.
