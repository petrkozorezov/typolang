# Код, цитирование и базовые формы

Код должен быть доступен для построения и исследования без случайного захвата
имён. Lisp служит отправной точкой записи, но соответствие конкретному Lisp
и буквальное тождество кода списку не являются требованиями. Ссылки, объявления
и контекст допустимо представлять явно, если это сохраняет нужные операции.

## Цитирование со связями

`quote` предоставляет структуру явно цитируемого выражения с сохранением
связываний. `unquote` вставляет фрагмент построителя, не исполняя самостоятельно
представленную программу. `eval` обозначает исполнение представленного
кода; его точный контракт ещё нужно закрепить. Отдельные `syntax`/`splice`
и обязательный набор `inspect/build/run` не вводятся без необходимого сценария.
Обычный рекурсивный обход исследует доступную структуру; отдельный примитив
`traverse` не требуется. Различимые узлы ссылок и объявлений допустимы: важна
программная доступность, а не буквальное совпадение кода с обычным списком.

`quote x` сохраняет ссылку, не превращает её в атом и не раскрывает автоматически
структуру аргумента. Объявления и ссылки переживают пересборку контейнеров:
метаданных только на корне недостаточно. Извлечённое тело сохраняет свои входы.
Готовая вставка не перепривязывается по именам в месте вставки.

```lisp
(let ((a 7))
  (quote {a:1 b:a c:(rec a)}))
```

Исполнение этого кода даёт `b=7`, `c=1`. Цитирование целой рекурсивной группы
переносит объявления вместе с внутренними ссылками; внешние захваты сохраняют
прежние цели. Фрагмент `(rec a)` не является указанием захватить одноимённое
поле там, куда его позже вставят.

`unquote` относится к ближайшему `quote`; выражение вставки использует контекст
построителя, не объявления шаблона. Вставки ленивы: невостребованная ветвь может
быть недоступна, хотя результат уже получен. Безусловная предварительная
проверка всех вставок не требуется. Начальное предлагаемое ограничение — вставка
одного выражения, не переменного числа полей, параметров или ветвей.

`(quote (unquote fragment))` вставляет фрагмент как данные. Если построитель
явно исполнил фрагмент, вставляется результат или остаток, не восстановленный
исходный вызов. Специального режима «остановиться после одного разыменования»
нет. Наблюдение исходника отдельно от результата редукции.

При правке определения внутри группы её внутренние ссылки сохраняют отношение
к изменённому объявлению в новой версии. Замена определяющего выражения не должна
терять идентичность объявления и требовать поиска ссылок по тексту имени.

Осталось определить каноническое представление кода, вложенное цитирование,
ошибки динамически построенных форм и отражение сахара. Рабочее предложение —
цитировать каноническую структуру, сохраняя пользовательскую запись отдельно.
Это ещё не принятое правило; наблюдение каждого промежуточного шага не требуется.

## Базовые и пользовательские формы

Устройство форм остаётся открытым вопросом. Ранее выбран контекст-карта,
содержащий формы и операции основания; вложенные области его расширяют.
Shadowing базовых форм запрещается валидатором, в том числе для построенного
кода. Это правило защиты от случайного изменения смысла, а не доказательство,
что формы являются обычными функциями.

Обсуждаются две границы: контекст содержит ссылки на заранее известные формы,
либо вычисляемое значение в позиции функции может определять правила связывания
в остальной форме. Первый вариант предложен как упрощение, но не принят.
Сама карта контекста не требует второго варианта.

Различие видно на `(lambda (x) x)` и `(f (x) x)`: в первом случае `(x)` объявляет
параметр, во втором это аргумент-вызов с нулём переданных аргументов. В выражении
`(lambda (maker) (maker (x) x))` произвольный `maker` не определяет связи `x`
заранее. Динамический выбор связывающей формы требует отложенного разрешения,
явного построения либо другого этапа обработки формы. Ленивость значений сама
по себе не решает, какое имя является объявлением.

### Проверка на локальном связывании

Поведение нерекурсивного `let` можно выразить обычной функцией:

```lisp
(lambda (value body) (body value))
```

Ей передаются значение и lambda, в которой локальный параметр уже объявлен.
Построитель аналогичного кода также может быть обычной функцией:

```lisp
(lambda (value-code body-code)
  (quote ((unquote body-code) (unquote value-code))))
```

Если `body-code` — цитированная lambda, её внутренние ссылки уже определены.
Но запись `(let ((x expression)) body)` дополнительно требует распознать
объявление `x` и область его действия. Цитирование готового `body` с внешним `x`
не позволяет новой lambda перехватить эту ссылку.

Следовательно, встроенное раскрытие выбранного `let` не требует отдельной
макросной системы. Расширяемая пользовательская связывающая запись требует
механизма передачи формы до окончательного разрешения вводимых ею имён.
Его построители могут быть обычными функциями; отдельный способ их вычисления
из этого не следует. Отсутствие макросов не является целью языка, а утверждение,
что ленивость сама заменяет связывающие формы, недостаточно.

Для выбора механизма форм осталось
различить готовые связанные фрагменты и ещё не разрешённую пользовательскую
запись, определить доступность псевдонимов форм и границу построения с исполнением.
Построение кода во время исполнения должно оставаться возможным; логическая
последовательность построения и исполнения не требует предварительно собрать
всю программу. Новые механизмы добавляются по необходимому сценарию, а не ради
полной взаимозаменяемости форм и функций.
